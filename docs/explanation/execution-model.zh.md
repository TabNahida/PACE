# 执行模型

[English](execution-model.md) · [设计说明](README.zh.md)

PACE 的代码在哪里运行、线程归谁所有、工作如何在线程之间转移。运行循环的具体机制见
[架构](architecture.zh.md#每个-worker-一个反应器)；本页讨论的是应用需要做出的选择。

## 一个上下文，同一时间一个线程

执行的基本单位是 `io_context`：一个反应器，拥有自己的轮询器、就绪队列、定时器和套接字注册。每个上下文恰好由一个
线程运行，分配给它的每个协程都在这个线程上恢复。没有任何东西会迁移：在上下文 2 上 spawn 的任务一直在上下文 2
上运行直到结束，在某个上下文上打开的套接字也只在这个上下文上使用。

这是有意的取舍。工作窃取和任务迁移能自动平衡不均匀的负载，但它们使每个套接字、定时器和协程帧都可能在线程之间
共享，于是每次操作都要付出同步的代价，所有权也变得难以看清。PACE 让每个反应器的状态保持单线程，热路径上不加锁
（[一次 yield 约 5 ns](../performance/runtime.zh.md#调度器组件)），而把工作放在哪里交给应用决定，因为应用最了解
自己的负载。

## 四种运行方式

| | 线程归谁所有 | 何时返回 | 适用场景 |
|:--|:--|:--|:--|
| `pace::run(entry)` | PACE，在调用线程上 | 入口任务结束时，并返回它的值 | 只有一个主协程的程序和测试 |
| `io_context::run()` | 你自己，在调用线程上 | 调用了 `stop()` 且上下文已排空 | 需要显式控制的单个反应器 |
| `runtime::run()` | PACE：每个上下文一个工作线程 | 调用了 `stop()` 且所有工作线程都已 join | 需要 N 个反应器的服务器 |
| `runtime::run_on_current_thread()` | PACE 管理 N−1 个工作线程；调用者运行上下文 0 | 同上 | 同上，但主线程不会闲置 |

有自己线程模型的应用也可以创建多个 `io_context`，在自己已有的线程上分别调用 `run()`；`runtime` 只是这种用法的
便捷封装。

`pace::run` 是最简短的形式：它创建一个上下文，运行入口任务，入口任务结束时停止上下文，排空后台任务的取消过程，
然后返回入口任务的结果。`io_context::run()` 和 runtime 在空闲时会继续运行：服务器在两次请求之间是空闲的，这不能
导致它退出。它们只在被要求时才停止。

直接客户端（`pace::http::get`、`tcp::exchange`、`udp::exchange`）是隐含的第五种形式：每次调用都在调用线程上运行
一个私有的上下文，持续到调用结束，并带有截止时间。它们面向完全不是异步的代码。

## 放置工作

`spawn`（提交一个任务）、`post`（提交一个函数）和 `stop` 是仅有的可以从任意线程调用的操作。上下文上的其他一切，包括套接字
I/O、定时器、`yield`、关闭套接字、取消注册，都属于运行该上下文的线程。在上下文运行之前创建对象、在它停止之后销毁
对象，可以由拥有它的线程进行。

要放置工作，就选择上下文：`runtime.context(i).spawn(task)`。典型的服务器给每个工作线程各自的监听器，使连接分散到
各个反应器上。要操作另一个上下文的套接字，应向那个上下文 post 一个函数，而不是直接去碰这个套接字。

跨线程提交经过每个上下文一个、由互斥锁保护的收件箱；只有收件箱排空之后的第一次提交才会唤醒反应器，因此一连串的
post 只需一次唤醒。

`spawn` 和 `post` 提交之后就不再过问。当一个上下文上的工作需要另一个上下文的东西时，
[跨上下文工具](../reference/runtime/cross-context.zh.md)在这个收件箱之上构建了常见的模式，并且总是在等待者原来所在的
上下文上恢复它：

- **归一个上下文所有的状态。** 把共享表、配额计数器或设备交给一个上下文（用 `runtime.shard_for(key)` 选出），其他上下文
  通过 `channel<T>` 向它发送请求。属主按顺序处理请求，无需加锁；其他上下文上的发送方在 channel 满时等待，
  而不是让队列无限增长，普通线程可以用 `try_send`。
- **每个上下文都要读、很少修改的数据。** `snapshot<T>` 把一个不可变的值（例如路由规则）发布到每个上下文。每个上下文
  读取自己的缓存副本，无需加锁；发布会在两轮之间替换这些副本。
- **来自另一个上下文的结果。** `co_await pace::on(context, work)` 在那里运行工作，然后带着它的值或异常在这里恢复。
  调用方的取消和截止时间会传给这项工作，调用方像等待子任务一样等它完成；这取代了先 post 一个函数、再把结果 post 回来的写法。

## 协作式调度

协程一直运行，直到它挂起（等待 I/O、定时器、`yield` 或等待另一个任务）或结束。没有任何东西会抢占它。运行循环
每批最多取 256 个就绪工作，这样即使就绪协程源源不断，定时器、I/O 和关闭请求也能得到处理；但一个从不挂起的协程
会独占整个反应器。

因此阻塞调用不应出现在反应器上：在协程里进行同步文件读取、跨 I/O 持有锁、做长时间计算，或者调用直接客户端
（`pace::http::get`），都会让同一上下文上的其他所有任务停顿。在协程里请使用 `async_*` 形式。PACE 目前还没有提供
运行阻塞工作的线程池；请在你自己拥有的线程上运行它，再用 `post`，或用 `channel::try_send`、`blocking_send`
把结果交回需要它的上下文。

## 停止

`stop()` 是一个永久的、协作式的请求，可以从任意线程安全地调用。反应器取消所有已注册的等待和定时器，它们以等于
`std::errc::operation_canceled` 的 `std::system_error` 恢复；随后反应器继续运行，直到这些被恢复的协程都完成展开。
`stop()` 之后的新提交会被拒绝。一个上下文只能运行一次：`run()` 返回后不能再重新启动。

协作式意味着：从不到达挂起点的代码，或者阻塞在 PACE 不掌控的系统调用里的代码，会推迟关闭。不应停止整个上下文的
取消，例如单个请求的截止时间，请改用[取消令牌和结构化作用域](../reference/runtime/structured-concurrency.zh.md)。

## 跨线程的错误

从根任务或投递的函数中逃逸的异常会停止它所在的上下文，`run()` 在排空之后重新抛出第一个这样的异常。在 runtime
中，第一个失败的工作线程会停止其他所有工作线程；`run()` join 每个工作线程之后再重新抛出。被等待的任务中的异常
像普通异常一样传播给等待它的协程。

## 如何选择

- 命令行工具或测试：用 `pace::run`；如果没有任何并发，也可以用直接客户端。
- 服务器：一个 `runtime`，你打算分给它的每个核心各一个上下文，每个上下文一个监听器，并使用
  `run_on_current_thread()`，让 `main` 本身成为其中一个工作线程。
- 嵌在自带线程的应用里的库：为每个专用于 I/O 的线程创建一个 `io_context`，在这些线程上用 `run()` 驱动，再用
  `post` 把结果交回去。
