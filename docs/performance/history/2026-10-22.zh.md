## 完整的长时间对比

一个服务器线程，32 个回环 TCP 连接，64 字节消息，每个连接一个未完成请求，
**每客户端 60,000 个测量请求 + 5,000 个预热请求**。每个后端十轮轮换试验，每轮约
六秒。所有响应字节和已完成请求数都经过校验。数值为各轮试验的中位数；延迟百分位数
是各轮百分位数的中位数，而不是合并样本后的结果。

第一个测量窗口，每个后端十轮试验：

| 后端 | 请求/秒 | p50 µs | p95 µs | p99 µs | 进程峰值 MiB |
|---|---:|---:|---:|---:|---:|
| PACE | 340,328 | 77.71 | 157.01 | 177.94 | 21.264 |
| Asio | 327,696 | 94.69 | 109.53 | 141.22 | 20.926 |
| libuv | 313,891 | 93.20 | 179.80 | 197.63 | 19.213 |

PACE 的 p50 **比 Asio 低 17.9%，比 libuv 低 16.6%**；在这次会话中，PACE 全部十个
p50 值都低于对照库的每一个 p50。吞吐量中位数分别高 3.9% 和 8.4%。这些观察结果
描述的是这台主机和这一负载，而不是这几个库的总体排名。

第二个窗口在间隔一段构建/测试时间之后，用同一个冻结的二进制和相同的负载重复测量，
每个后端七轮轮换试验：

| 后端 | 请求/秒 | p50 µs | p95 µs | p99 µs | 进程峰值 MiB |
|---|---:|---:|---:|---:|---:|
| PACE | 340,618 | 77.59 | 156.74 | 181.13 | 21.266 |
| Asio | 326,745 | 94.77 | 110.62 | 145.31 | 20.906 |
| libuv | 314,866 | 93.38 | 180.06 | 198.45 | 19.219 |

PACE 的 p50 再次更低，**比 Asio 低 18.1%，比 libuv 低 16.9%**。吞吐量的提升、
尾延迟不如 Asio 以及内存更高这几点也再次出现。这是在同一主机、同一天的重复测量，
不是在独立硬件上的验证。
[第二个窗口的原始 JSON](../../../benchmarks/results/linux-optimization-2026-10-22/final-c32-b64-session2.json)。

在第一个窗口中，PACE 的 p95 **比 Asio 高 43.3%**，p99 **高 26.0%**。两者都低于
libuv，但 PACE 不能宣称在尾延迟上普遍领先。它也没有达到早先“吞吐量至少比 Asio 高
5%，同时 p99 相差不超过 5%”的目标。

十组交替进行的**旧 PACE/新 PACE** 配对显示了这项改动本身的代价：吞吐量从 309,356
提高到 341,290 请求/秒（配对增益中位数 10.26%，探索性 bootstrap 95% 区间为
9.07–11.51%，十组全部提升），p50 从 100.46 µs 降到 77.53 µs。然而，p95 从 115.86 µs
升到 156.78 µs（35.3%），p99 从 147.82 µs 升到 179.84 µs（21.7%）。因此，在这一负载
下，默认的热路径是以尾延迟为代价，换取吞吐量和延迟中位数。

## 是什么拖慢了 PACE

两项改动在不改变公开 API 的前提下，减少了 TCP 热路径上的工作：

1. **持久的 Linux 就绪关注**。旧的反应器使用 EPOLLONESHOT，每次接收都要通过
   `epoll_ctl` 重新武装。现在，当恢复执行的协程在同一方向上等待时，反应器会保留
   水平触发的订阅，并在轮询前协调发生变化或空闲的方向。在 32 客户端诊断中，
   `poller_update` 调用次数从约 **351,977 次降到 33 次**。代次令牌仍会拒绝过期事件；
   空闲的可写关注会被移除，以避免空转。独立的轮询器仍保留默认的一次性模式；
   kqueue 和 Windows 沿用现有后端。
2. **TCP 短读之后的就绪等待**。一次短读通常已经排空了接收队列，但下一次操作会
   立即再次调用 `recv`，通常得到 EAGAIN。现在由每个流私有的一个提示先等待水平就绪。
   已排队的字节和 EOF 仍会被轮询器检测到，并由 `recv` 确认；读满缓冲区的读取保留
   立即执行的路径。空缓冲区和移动操作都有明确的回归测试覆盖。在同样 352,000 次
   预热加测量的往返中，诊断得到的接收调用次数从 704,004 降到 352,032。

最初的插桩基线中，反应器墙钟时间约有 6.1% 花在轮询器更新上，14.6% 花在接收调用上，
67.7% 花在发送上。这些是**插桩后的墙钟诊断数据**，包含内核等待/被调度出去的时间
以及启动/预热；它们不是 CPU 采样，不得与未插桩的 Asio/libuv 吞吐量直接比较。内核
TCP/发送工作仍是观察到的最大开销。存档中分别包含基线、持久关注中间版本和最终短读
版本的诊断数据。

第一项优化是 Linux 专用的。短读提示使用水平就绪语义，但其性能只在 Linux 上测量过。
协议分层以及 DNS/QUIC/HTTP3 的新增内容是独立的功能改动；这些 TCP 基准测试不能
证明它们的速度。

## 内存与测量的局限

峰值内存是完整可执行映像在 Linux `/proc/self/status` 中的 VmHWM。它包括服务器、
阻塞客户端线程、应用的连接缓冲区、预热以及保存的延迟样本，**不是库本身独立的
内存**。PACE 记录的内存仍高于两个对照库；由于没有做分配统计，这一差异无法定量
归因于协程帧或反应器的描述符映射。本页不宣称任何内存优势。

测量环境是同一台机器上的本地 WSL2 Linux，GCC 13.3.0，C++20，`-O3`，对照为
Asio 1.34.2 和 libuv 1.52.1。对比运行中禁用了性能剖析和 sanitizer。所有计时运行
都是串行的；并发编译和协议测试在此期间暂停。没有强制固定频率、CPU 亲和性或使用
专用主机。闭环本机测试不衡量过载、生产网络、连接建立、多工作线程扩展，以及 UDP、
TLS、HTTP、QUIC 或 HTTP/3 的性能。观察到的范围和探索性 bootstrap 区间并不能消除
这些局限。

## 复现当前的测量

```sh
xmake f -c -m release -o build/fair --benchmarks=y --profiling=n --sanitizers=n -y
xmake -y pace_bench
python3 scripts/run_benchmarks.py --build-dir build/fair --require-all \
  --repeats 10 --clients 32 --bytes 64 --requests 60000 --warmup 5000 \
  --label local-linux-confirmation --output benchmark-results/local-linux-confirmation.json
```

新的测量请保存到新的输出目录中。证据存档记录了源码/二进制哈希、编译器命令、精确的
负载、原始试验以及优化前/后的基线。其中的 `reproduce_build.py` 会重建所记录的基线和
最终基准测试程序，包括源码目录的迁移。`python3 scripts/run_profile.py --input REPORT.json`
只用于单独以 `--profiling=y` 构建的诊断报告。参见[性能剖析](../../../benchmarks/profiling.md)
和[基准测试的计时/内存语义](../../../benchmarks/README.md)。
