# HTTP 与 WebSocket 性能调查

[English](protocols.md) · [性能](README.zh.md) · [CI 架构覆盖](../contributing/ci.zh.md)

这些测量都在本地 Linux 上进行。HTTP/1 和 WebSocket 是拿 PACE 与它自己 v0.1.1 的行为作比较；
HTTP/2 和 HTTP/3 实验则是在同一个更新后的二进制中比较不同的处理函数（handler）上限。
较早的 TCP Asio/libuv 对比并不能说明 HTTP 或 WebSocket 的性能排名。远程 CI 检查的是功能和可移植性。

## HTTP/1 响应完成

[Issue #15](https://github.com/TabNahida/PACE/issues/15) 指出了一次本可避免的等待：
在一个分帧完整的 `Connection: close` 响应之后，客户端已经解析出了完整的消息，
但 `send()` 仍会等待传输层优雅关闭，包括对端的 FIN 或 TLS close notify，最长达 100 ms。

现在默认行为是以零对端等待预算尝试本地关闭，并直接返回已完成的响应。`client_options` 可以选择显式的
`graceful` 策略和超时时间。以 EOF 界定的响应仍需要 EOF 来确定消息边界；服务器端的准入拒绝仍保留有界的排空。

在刻意延迟对端关闭的情况下，每种情形进行十次试验，`send()` 耗时的中位数如下（不含连接建立和 TLS 握手）：

| 传输层 | 对端关闭延迟 | v0.1.1 | 更新后的默认行为 |
|---|---:|---:|---:|
| TCP | 50 ms | 50.1444 ms | 0.0187 ms |
| TLS | 50 ms | 50.2601 ms | 0.1098 ms |

对于对端延迟为 1、10、50 或 200 ms 的每一个更新后关闭响应样本，客户端都在对端开始关闭之前就已完成。
以 EOF 界定的响应仍会等待 EOF，显式的优雅关闭策略也保留了等待。这里单独衡量的是一个两字节响应的拆除延迟，
并不是 HTTP 吞吐量的倍增。两端都设置了 TCP_NODELAY。最初一次未设置该选项的诊断运行单独保留，
因为延迟 ACK/Nagle 行为干扰了其中的 TLS 计时。

[完整的 HTTP 数据、配置和构建来源](../../benchmarks/results/http-close-linux-2026-10-23/README.md)。

## WebSocket 帧处理

之前的解码器把前缀、可选长度、掩码和负载分别读入各自大小精确的缓冲区。因此即使短帧的字节已经全部可读，
也需要多次接收调用。每个数据帧还会分配一个临时负载，再把它拷贝到最终消息中；发出的帧每次都分配新的存储。

更新后的实现使用 8 KiB 的预读缓冲区，把数据分片直接拷贝到最终消息中，并复用发送帧的容量。较大的负载可以绕过预读缓冲区。
掩码处理借助对齐安全的拷贝和重复的密钥，每次处理八个字节，尾部再逐字节处理；该实现在任意字节序下都能工作。
帧校验、掩码随机性、UTF-8 检查和各项限制都保持原有语义。代价是每个流多占用 8 KiB，并保留发送缓冲区的容量；
这里并不声称降低了连接的内存占用。

每种工作负载交替进行十次试验，每秒往返次数的中位数：

| 负载 / 分片方式 | v0.1.1 | 更新后 | 变化 |
|---|---:|---:|---:|
| 64 B / 单帧 | 256,431 | 330,083 | +28.7% |
| 16 KiB / 单帧 | 44,342 | 158,337 | +257.1% |
| 64 KiB / 1 KiB 分片 | 3,339 | 6,252 | +87.2% |

[WebSocket 测量数据和可复现的命令](../../benchmarks/results/websocket-linux-2026-10-23/README.md)
包含每种固定工作负载交替进行的十次试验，以及单独的系统调用计数诊断。两端共用同一个反应器和线程。
每条二进制消息都带有递增的序号，回显的整个负载都会被校验。TLS、多工作线程扩展以及其他 WebSocket 库
不在本实验范围内。公开的流接口仍然一次只允许一个异步操作。

## HTTP/2 与 HTTP/3 处理函数并发

瓶颈在 PACE 的适配器中：它的协议循环会等待每个应用处理函数完成后，才处理下一个已完成的请求。
因此一个缓慢的异步处理函数会拖慢同一连接上互不相关的流。

现在适配器最多同时派发 `max_concurrent_handlers` 个处理函数，并且还受流数量上限的约束。由一个驱动者
持有 nghttp 会话和传输层；处理函数把已完成的响应放入一个有界队列并唤醒该驱动者。这样在处理函数等待 I/O 时，
网络进度和相互独立的流都能继续推进。它不会让 CPU 密集型处理函数在同一个反应器上并行执行。
并行的 CPU 执行仍然依靠工作线程的分配。

在一次受控的本地 Linux 探测中，每批包含 16 个请求，每个请求的处理函数都等待一个 10 ms 的定时器。
每种配置运行十批，使用同一个更新后的二进制，不计连接建立和握手，得到的中位数如下：

| 协议 | 处理函数上限 1 | 处理函数上限 8 |
|---|---:|---:|
| HTTP/2 over TCP | 163.036 ms | 20.500 ms |
| HTTP/2 over TLS | 163.167 ms | 20.847 ms |
| HTTP/3 | 164.040 ms | 21.016 ms |

所有响应以及观测到的处理函数峰值并发都经过了校验。约八倍的提升是这种合成异步工作在重叠执行后的预期结果，
既不是一般意义上的吞吐量结果，也不是新旧二进制的直接对比。
[原始批次数据、环境与复现方法](../../benchmarks/results/protocol-multiplex-linux-2026-10-23/README.md)。

HTTP/2 采用非阻塞的 TCP/TLS 推进，配合显式的就绪唤醒，并保留 TLS 重试缓冲区。它还会以 64 KiB 为阈值批量发送生成的帧，
其中可能包含最后一个帧。TLS 路径为每个连接预留 128 KiB 的有界密文缓冲区，使同时进行的写操作在套接字背压下仍能继续接收。
HTTP/3 唤醒其现有的 QUIC 事件驱动者。两个 HTTP 适配器都没有增加周期性的轮询定时器。上面的历史基准测试使用的是
Linux timerfd；当前的 QUIC 后端在 POSIX 上使用 PACE 可取消的回调定时器，同样没有周期性轮询。这一集成改动和 ngtcp2 后端
都有功能测试覆盖，但尚未与这些历史结果做基准对比。把处理函数上限设为 1 即可保留顺序的应用派发。

关于上限、处理函数生命周期和取消契约，请参阅 [HTTP/2](../reference/http2/README.zh.md) 和 [HTTP/3](../reference/http3/README.zh.md) 参考文档。
回归测试覆盖了处理函数重叠执行、流数量上限、乱序完成、大响应、TLS 背压以及对端断开后的完成。
